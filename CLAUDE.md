# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

Rule-based ABRSM piano sight-reading test generator. It does not scan or hand-engrave scores — it procedurally generates a legal note/rhythm sequence from a per-grade rules table, serializes it straight to a MusicXML string, and renders that with OpenSheetMusicDisplay (OSMD) in the browser. Plain static site: `index.html` + `src/`, deployed as-is to GitHub Pages — no build step, no framework, no bundler.

The UI (`index.html`, user-facing strings in `src/app/app.js`) is in Traditional Chinese; code, comments and identifiers are English. `README.md` (also Chinese) has the architecture rundown this file summarizes for Claude.

## Commands

```bash
npm install
npm test                                                     # generator + MusicXML unit tests (node --test)
npm run serve                                                # local static server, http://localhost:5173
npm run sample -- --grade 3 --seed 42 --out test.musicxml   # print/save one generated test as MusicXML
npm run audit                                                # Monte-Carlo distribution audit, all grades
npm run audit -- --grade 2 --section rhythm --runs 5000       # narrow it down
npm run devices                                              # Playwright layout/behaviour check across 5 device sizes
npm run smoke                                                # Playwright render check across all 8 grades
npm run smoke -- --grade 3 --screenshot app.png              # smoke test a single grade, with a screenshot
npm run loudness                                             # LUFS loudness measurement of the real playback chain, all grades
npm run loudness -- --target -14 --grades 1,3,5,7             # narrow it down
```

Single test file: `node --test test/generator.test.js` (or `musicxml.test.js`, `notation.test.js`). `node --test` also supports `--test-name-pattern <regex>` to filter by test name.

## Architecture

### Generation pipeline

`generateTest(rulesTable, {grade, seed}) → score object → toMusicXml(score) → MusicXML string → OSMD renders it`

Entry point `src/generator/generate.js`; public surface re-exported from `src/generator/index.js`. All randomness runs through `random.js`'s seeded mulberry32 PRNG (`createRandom(seed)`) — every generation decision is a pure function of that one seed, so the same seed always reproduces the same test (`npm run sample -- --seed N`, and unit tests, rely on this). The UI and `fingerprint.js`'s `generateUnique` never pass a seed, so each call gets a fresh `randomSeed()`; dedup against recent history happens by retrying generation, not by choosing a seed. Order of generation (see `docs/abrsm-sight-reading-analysis.md §3`):

1. Pick key, time signature and bar count from `src/rules/abrsm-piano-grades.json` for the grade.
2. Build a harmonic skeleton (`harmony.js`): opens on I, cadences V–I, normally one chord per bar but occasionally two (see "Two chords in one bar" below). From 6 bars up it is built as a **period** (see "Phrase structure" below), not a free chord walk.
3. **Left hand is written first**: bars of rhythm cells (`rhythm.js`) with pitches assigned against the chord progression (`melody.js`'s `assignPitches`). Its notes become a sounding-bass timeline (`soundingTimeline`).
4. **Right hand is written second**, checked note-by-note against what the left hand is sounding at that same instant — clashing vertical intervals are rejected or repaired during pitch selection, not patched after the fact.
5. `harmoniseLeadingNotes` reconciles minor-key leading-tone raises between the two hands (a cross-hand disagreement is a "false relation"). `harmoniseRepeatedLeadingNotes` catches the same problem *within* one hand: a clash repair flips only the clashing note's raised 7th to natural, which can leave an immediately-repeated note disagreeing with itself. Both run once per hand inside `assignPitches` and once more in `generate.js` after the cross-hand pass, since each repair can reintroduce the other's problem. `harmoniseLeadingNotes` iterates to a fixed point (not a single pass) — fixing one cross-hand pair can break agreement with a third overlapping note, so it loops until nothing changes.
   - **Minor keys are written as harmonic minor unconditionally**: the 7th degree raises wherever it occurs (`degreeOf(dstep, key) === 6`), not just under a dominant-function chord the way it used to. `pickWeighted`'s clash-screening must agree: it screens degree-7 candidates at their *raised* pitch (`soundingMidi` helper), not the natural one, or it'll happily pick a candidate that only clashes once raised and let `resolveClashes` silently un-raise it back to natural.
6. `applyExpression` adds dynamics, wedges, slurs, staccato and rall. within what the grade's rules allow — and, from Grade 6, sustain-pedal spans, a mid-piece rit./a tempo, and (Grade 7+) grace-note ornaments; see "Grade 6-8 extras" below.
   - **A slur used to be able to reach straight through a rest.** Whether a bar-pair could be slurred was decided by "does each bar have *some* sounding note" — enough to keep Grade 1's alternating hands from getting slurred across a bar they sit out entirely, but a bar shaped `[note, rest, note]` passed the same check, and the slur curve was drawn from the pair's first sounding note to its last regardless of what sat between them. Fixed by requiring every event between the pair's first and last sounding note, inclusive, to itself be a sounding note — `test/generator.test.js`'s "a slur never spans a rest" guards it.
7. `toMusicXml` (`musicxml.js`) serializes the score to MusicXML 4.0: one `<part>`, two staves, staff 2 reached via `<backup>`.
   - **The tempo/character-word direction is deliberately always on staff 1 (treble), a fixed spot regardless of what bar 1 contains.** Making it follow whichever hand sounds first — mirroring `applyExpression`'s `sounds()` check, which correctly routes the *dynamics* mark below it to the sounding staff — was tried and reverted: the dynamics mark is about the sounding hand's loudness, so it belongs on that staff, but the tempo/character word is a heading for the whole piece, and real engraving keeps it on the top staff regardless of which hand opens. Making it jump staves depending on content produced a less consistent result across tests, not a more correct one — the user's own read on it.

Key data structures/conventions to know before touching the generator:

- **dstep (diatonic step)**: pitches are generated in diatonic-step space, not MIDI (`theory.js`: `dstep = 7*octave + letterIndex`), so spelling is correct by construction — e.g. the raised 7th in D minor always comes out as C#, never Db.
- **score object**: `{seed, grade, confidence, key, timeSignature, barCount, divisions, tempoTerm, tempoBpm, progression, staves: {1: rightHandBars, 2: leftHandBars}}`. Each bar is `{events, beatDuration, directions}`; each event carries `dur`, `type`, `rest`, and — if pitched — `pitch`/`dstep`/`chordDegrees`, plus optionally `grace`. `progression[barIndex]` is normally a plain roman numeral, but for a split bar (see "Two chords in one bar") it's a `[first, second]` pair — code reading `score.progression` directly, rather than through `harmony.js`'s `firstChord`/`lastChord`/`chordAt`, needs to handle both shapes or a split bar compares as "always different" from its neighbours (array `!==` string is always true).
- **rhythm cells** (`rhythm.js`): whole-beat idiomatic figures from a fixed library, not built note-by-note, so bars always sum correctly and beaming/dots/tuplets only appear once a grade's rules permit them. `meter.js` rescales the library for other beat units and swaps in a separate cell set for compound time (x/8).
- **rhythmic repetition** (`generate.js`'s `buildStaff`) differs by hand role. A real accompaniment (Grade 2-3's left hand once hands sound together, `isAccompaniment`) draws one rhythm (`ostinato`) and reuses it for every bar. The melodic hand instead gets an occasional *phrase echo* — restating whichever regular bar most recently played at the same position two bars back (`bank[barIndex % 2]`, refreshed on every regular bar, not frozen at the first two — freezing it made every later phrase echo bars 1-2 specifically, reading as far more repetitive than a real test). Every bar that reuses a rhythm now also carries a `motif` directive so the *pitches* rhyme too (see "Phrase structure" below); a `test/generator.test.js` guard caps exact rhythmic cloning at 35% of a melodic hand's bars, so the ad-hoc 2-bar echo chance was lowered to 0.18 when the structural phrase restatement was added — total repetition unchanged, but it now lands where a period wants it rather than at random.
- **fingerprinting** (`fingerprint.js`): hashes musical content (key, metre, bar count, every pitch/duration), not the MusicXML text, so two renders differing only in dynamics still dedup as the same test (`generateUnique` + the browser's localStorage history).
- **`pickWeighted` (`melody.js`) picks a move category before a pitch**: step vs. leap vs. repeat is weighted first (via `generatorHints.stepwiseBiasPercent`), then a candidate is picked within that category — scoring every candidate on one shared scale let `stepwiseBias` mean nothing, since leap candidates usually outnumber the two step candidates. A passing/neighbour tone's resolution (continuing in its approach direction) is *forced* when a non-clashing option exists, or `repairNonChordTones` would later silently turn an intended stepwise pair into two leaps.
- **Run-continuation bias** (`runDirection`/`runLength` in `melody.js`): `pickWeighted` tracks how long the current same-direction step run is and grows the weight of continuing it (capped, tapering off), so scale-run figures read as real runs instead of independently-scored single steps. Layered on top of every other constraint — clash avoidance, range, chord-tone-only for the bass — not a bypass of them.

### The audit is how musical faults get found (`scripts/audit.js`)

`npm test` answers "is this legal?" — bars add up, no augmented seconds, nothing out of range. It cannot answer "is this a plausible test?", because that is a question about **distributions**, and every musical fault found in this project so far has been a distribution that was wrong rather than a rule that was broken. `npm run audit` generates thousands of tests per grade and prints observed numbers against expectations, in five sections: `harmony`, `rhythm`, `melody`, `texture`, `expression`. It exits non-zero when something disagrees. **Run it after any generator change**, and prefer adding a check there over reasoning about whether an isolated example looks right.

Faults it has caught that no unit test could:

- **The bass had no notion of root position.** It was picked as melody — nearest chord tone, weighted for stepwise motion — so only a piece's very first note ever deliberately took a root. The cadential V had its own root about a third of the time, which is why the closing V–I did not sound like a cadence. Fixed in `assignPitches`: where the harmony arrives (`harmonyArrives` — a downbeat, or the second half of a split bar), a `chordToneOnly` hand prefers the chord root, forced on the cadential bar and left to the ordinary weighting a fifth of the time so inversions survive.
- **`previousWasChordTone` was computed against the wrong chord.** `pickWeighted` recomputed it from the *incoming* note's chord, so at every harmony change the previous note — a perfectly good chord tone of the chord it belonged to — read as an unresolved passing tone and the resolution force fired. That override beats motif, cadence and bass-root preferences alike, and it fired exactly where those matter most. It is now tracked in `assignPitches` against the chord each note actually belonged to. This one fix improved bass roots, motif survival and restatement rates together.
- **Stacking below the bass rewrote the inversion.** `stackChordTones` adds notes *below* the main note; under the bass that makes the added note the lowest, so a third below a root-position chord silently produced first inversion. `bassVoicing` allows only the chord root below in the lower hand.
- **The accompaniment repeated its rhythm far too much** (85-89% of bars on one figure). Four separate causes, and the non-obvious one dominated: the `calm` cell set a low-grade left hand draws from held only six or seven cells whose weights concentrate on one or two bar-fillings, so *independently drawn* bars kept coinciding — the vocabulary, not the `ostinato` mechanic, was the binding constraint. Adding the two-quaver cell to `calm` (a staple accompaniment figure) roughly doubled the options. Alongside that: `ostinato` has a per-test budget (`ostinatoBudget`, ~40% of bars) rather than a probability, since a roll can never *guarantee* a test won't land badly; it may not run more than two bars unbroken; and a bar meant to be fresh redraws (`drawContrastingBar`) until it differs from the two bars before it and from the ostinato.
  - **Means hid this for a whole round.** The average share sat at an acceptable 52% while individual tests still put one figure in six bars of eight — and a reader meets single tests, not averages. The rhythm section now checks the tail (`tests where one rhythm takes >60% of bars`) as well as the centre.
  - Two things the metric must *not* count as repetition: a bar holding one sustained note (that is "melody over a sustained bass", the Grade 2 texture the rules table asks for, and in 2/4 it means a half note in every bar), and whole-bar rests in a hand that alternates. Only bars with two or more events count as figures.
  - Residual, deliberately left: repetition concentrates in the short metres (2/4 ~30%, 4/4 ~12%), where a two-beat bar has genuinely few fillings, and some of it is the phrase restatement correctly bringing the antecedent's figure back. The audit prints the per-metre breakdown so this stays visible.
- **Declared features that never appeared**: Grade 8's `fff` was unreachable because the wedge target always stepped exactly one dynamic.
- **Chord-to-chord motion had no notion of idiom.** `buildProgression` picked the next chord uniformly from `{I, ii, iii, IV, V, vi}` (`{I, IV, V, vi}` below Grade 4) with only a same-chord-repeat and V→IV/ii filter. A flat pool cannot tell a common progression from a rare one, so `iii` — the weakest, most tonally ambiguous diatonic triad, sharing two tones with both I and V and pushing toward neither — turned up almost as often as `IV`, and root motion by a bare third (no strong directional pull) matched the rate of motion by a second, both crowding out the fourth/fifth motion that actually drives tonal harmony forward. Measured across 600 tests/grade before the fix: `iii` at 8.7-10.2% of chords by Grade 5, weak third-motion at ~14% of changes. Replaced with `FOLLOWS`/`FOLLOWS_SIMPLE`, weighted transition tables keyed by the previous chord (real practice treats `iii` as a passing chord *from* I/vi *to* IV, not a destination to land on), and the anti-static "avoid V-V into the cadence" fallback was weighted toward ii/IV (the classic pre-dominant approach) instead of picked uniformly from `{IV, ii, I, vi}`. After: `iii` down to 2.5-2.7%, weak motion down to 5-6%, fourth/fifth motion up to 41-45%.
- **Harmony changed on every single bar, with no way to hold still.** `mayFollow` filters out an immediate chord repeat when picking what the harmony moves *to* — correct, since "the next chord is the one already sounding" isn't a move at all — but nothing offered a chance to simply *not move* first, so a test's harmonic rhythm was one new chord every bar, without exception, for its entire length. Real tonal writing — especially a short, simple test — prolongs a chord across more than one bar constantly, most often the opening tonic while the key gets established. `buildProgression` now rolls a separate, capped chance (0.45 right after the I that opens the piece, 0.2 elsewhere, never more than two bars running) to hold the current chord before falling through to the ordinary weighted "move to the next chord" pick. Measured after: chords held over from the previous bar 13-19% of bar transitions, all grades — audited as `harmony`'s "chord held over from the previous bar" so it can't silently drift back to 0% or run away.
- **Leaps couldn't build an arpeggio.** `pickWeighted` treats any leap of a third or more as needing compensation — the next note should reverse direction, ordinary vocal-style part-writing practice — and applied that uniformly to *every* leap, including one that was itself continuing a broken-chord figure already in progress. That is a different thing entirely: Alberti bass, broken-octave accompaniment and arpeggiated melody are keyboard-idiomatic writing that keeps going the same direction for several notes, and the reversal rule was quietly forbidding exactly that — after one leap outlining a chord, the very next note was 6x more likely (2.5 vs 0.4 weight) to turn back than to complete the triad. Fixed by tracking `arpeggioDirection`/`arpeggioLength` the same way `runDirection`/`runLength` already track a step run: a leap that continues the same direction *and* keeps both ends on chord tones now gets an escalating boost (both within the leap category and for the leap-vs-step-vs-repeat category lottery itself) instead of the reversal penalty. Measured after: leaps continuing the same direction as the leap before them, 7-30% of eligible pairs across grades (rising with grade, since a wider window offers more chord tones to arpeggiate through) — was close to structurally unreachable before.
- **A repair pass could relocate a note into a fresh augmented 2nd it never checked for.** `moveOffParallel` (the parallel-5th/8ve repair) already guards its relocations with `writesAugmentedSecond`; `repairNonChordTones` — which relocates a note that doesn't belong to the chord sounding under it — never did, and it is the pass most likely to move a note onto exactly the raised-7th/natural-6th pair that makes one. The concrete case that surfaced it: Grade 1's alternating hands force `endOnTonic` on *each* hand's own last sounding note, including whichever hand finishes its part before the piece's actual final bar — so that note's forced tonic can legitimately not be a tone of the *local* harmony there (the piece hasn't reached the true closing I yet). `repairNonChordTones` read that mismatch as an ordinary passing-tone fault and relocated the note off tonic entirely, and `shapeCadence` — which runs later and trusts that note's `dstep` to still be the tonic it is approaching — built a leading-tone approach around the now-wrong anchor, writing an augmented 2nd nothing downstream was positioned to catch. Fixed in two places: `repairNonChordTones` now exempts `finalEvent` outright (mirroring the special-case it already gets in `resolveClashes`), and gained the same `writesAugmentedSecond` guard `moveOffParallel` has, for every other note it might relocate.

The `voiceleading` section checks part-writing grammar rather than distributions — the things a theory examiner rings in red, all of which were invisible to both the unit tests (each note is individually legal) and the distribution checks (the averages looked fine). What it found and how each was fixed:

- **Consecutive fifths and octaves** between the outer voices, in 26-45% of tests. `pickWeighted` now refuses to *choose* one (it needs `previousBass`, the other hand's bass at the previous moment, which nothing tracked), and `relaxParallels` clears up what the repair passes put back afterwards. That second half matters: the per-pair rate was only ~0.5% while a quarter to a half of tests contained one. **`relaxParallels` must walk attacks in *both* hands** — an earlier version walked only the melody's and changed almost nothing, because the succession the ear hears runs from a bass move under a held melody note to the next sonority.
- **The leading note failing to rise** at the V–I arrival (41% in the melody). Weighting it inside the step category was useless — the category lottery discards the whole step category first — so it is forced ahead of the lottery, like the passing-tone resolution.
- **Doubled leading notes** (up to 17%), which are a parallel octave waiting to happen. Blocked in four places, since every pass that can place a note could write one: `pickWeighted`, `stackChordTones`, `resolveClashes`, `repairNonChordTones` — and `shapeCadence`, which was the stubborn one, because `cadenceApproach` *prefers* the leading note and the cadential V underneath contains it.
- **V falling back to IV/ii** (3-4% once split bars arrived). `harmony.js`'s `mayFollow` allows only I/vi after V.
- **Melodic tritone leaps**, now refused outright alongside the augmented 2nd.
- **`relaxParallels` could relocate a note onto a pitch that clashed against a bass note it never checked.** `outerVoiceTimeline`'s `sounding` field — what `moveOffParallel`'s clash guard checks a replacement pitch against — was built from only the bass notes active at the one instant a timeline entry happened to key off, not the full duration of the melody note being considered for relocation. A held melody note that outlasts more than one bass attack got checked against just the first of them; a replacement pitch clear of that one bass note but a semitone from a later one (still within the melody note's own sounding duration) sailed through. `sounding` is now built from every bass span overlapping the *whole* duration of the top event the entry is keyed to, not just the instant. (`bass`, used separately for detecting the parallel motion itself, stays instant-based — that one is correctly about the interval formed at each individual attack.)
- **`resolveClashes` could leave a flagged clash unrepaired.** Its replacement search is restricted to the sounding chord's own tones (or the tonic, at the final cadence) — reasonable, since a repair shouldn't wander off the harmony. But a bass note sustained across a mid-bar harmony change (its own chord tone when written, still ringing after the harmony moved on) can land a semitone from *every* tone of the new chord simultaneously — vi against a still-ringing raised-7th V does this structurally, not by chance, since raising the leading tone puts V's tones each a semitone from vi's neighbouring tone. When that happens the tone-restricted search comes back empty and the flagged note was left exactly as clashing as it started. It now retries once, widened to the whole window (same fallback `pickWeighted`'s own last-resort path already uses), before giving up — except at the final tonic, where a clash is still preferred over losing the cadence.

Three checks in that section were wrong before they were right, and the corrections are recorded in the code so they are not "fixed" back: the leading note must only resolve *at the point the dominant gives way to the tonic* (demanding it of every degree-7 note condemns an ordinary descending scale, and the bass under a prolonged V cannot leave its chord tones at all); and two spacing rules imported from four-part vocal writing — outer voices within two octaves, and adjacent upper voices within an octave — do not apply to keyboard melody-and-accompaniment texture at all. The spacing check that survives is whether one hand can physically reach its own chord.

Two things the audit deliberately does *not* flag, because they are constraints rather than faults — do not "fix" them: in a five-finger grade the chord root is outside the hand's five notes in 14-19% of bars (so the root rate is measured only where it is reachable), and `stepwiseBiasPercent` is the weight the step *category* gets before the harmonic filters run, not a target for the finished line, so the realised rate always sits below it.

### Phrase structure, motif restatement and cadence

These three are what stop a test reading as separately-invented bars laid end to end. They interlock — the harmony is arranged so the melody's restatement is legal by construction — so changing one without the others mostly undoes it.

- **Period** (`harmony.js`'s `buildProgression`/`halfCadenceBar`): from 6 bars up, the antecedent ends on V (a half cadence) at `floor(barCount/2) - 1`, the consequent restarts on I, and the consequent's first two bars are given **the same chords as the antecedent's first two**. That last part is not decoration: it is what lets the melody restate literally there instead of being bent note by note to fit a different harmony. `halfCadenceBar` returns null below 6 bars, where there is no room for two phrases.
- **Restatement** (`generate.js`'s `planRestatement`): which consequent bars bring back the antecedent's opening is decided **once for the whole texture**, in `generateTest`, not per hand. Rolling it inside each `buildStaff` call had the hands agreeing only about half the time, and since the right hand is checked against the left, a melody trying to restate over a bass that had moved on kept getting rejected.
- **Motif transposition** (`generate.js`'s `pitchTreatment`): the shift is the **diatonic distance between the two bars' chord roots**, never a freely-picked ±1/±2. A diatonic triad is a stack of thirds, so shifting `{root, +2, +4}` by k gives the triad rooted at root+k — chord tones map onto chord tones and the restatement survives the chord-tone filters. A free shift measured 14% of motifs keeping their contour. Same chord ⇒ shift 0 ⇒ literal repeat; different chord ⇒ a tonal sequence.
- **Applying it** (`melody.js`'s `assignPitches`): motif notes are placed **absolutely** (`source[j] + transpose + octave`), not relative to whatever this bar's first note turned out to be. Re-basing on the realised first note is the trap — one rejected note displaces every later note, which then lands off the chord and gets relocated by `repairNonChordTones`, roughly halving surviving restatements. The octave is chosen once per bar by `fitMotifOctave`, scoring **how much of the whole shape fits the window**, not where the first note wants to sit.
- **Preferred candidates**: a motif or cadence pitch is offered to `pickWeighted` as `preferred` and taken only if it survives every hard filter there (range, leap limit, chord tone on the beat, vertical check). It is checked *after* the passing-tone resolution force — except that a preferred pitch which is itself a valid resolution wins, since a transposed bar resolves its own passing tones the same way the source did (this was the largest single cause of restatements breaking up).
- **Contour arch** (`melody.js`'s `archTargets`): the pitch the line is drawn toward moves with position — roughly 34% of the window at the start, peaking near 86% about two thirds through, falling to 30% at the cadence. A fixed pull to the window centre (what this replaced) gives every note the same target, so the line mills about and touches its top note two or three times at arbitrary places. Passed as `arch: 0` for the left hand, which should stay put under the tune, making it exactly the old behaviour there.
- **Cadence** (`melody.js`'s `shapeCadence`): the melody's approach to its final tonic is forced **after** `repairNonChordTones`/`resolveClashes`, not merely preferred during the walk — those passes moved it often enough that a stepwise approach survived only ~20% of the time (now 88-100%). It must re-apply `fixAugmentedSeconds`'s rule itself, since it runs after that pass: raising the 7th when the note before is the natural 6th a step below writes an augmented 2nd. Skipped for the bass (`chordToneOnly`), which is *supposed* to leap V–I.

Not every test can end stepwise: in a five-finger grade whose tonic sits at the bottom of the position, the leading note below is outside the five notes allowed and the supertonic above can clash with the bass. The test asserts the rate, not every case.

### Chord density per grade

`stackChordTones` (`melody.js`) used to consider exactly one candidate — the third below — which capped every chord at two notes whatever the grade allowed, so Grade 6-8's declared three- and four-note chords never appeared and **Grade 8's texture was identical to Grade 3's**. It now walks a full octave down taking the nearest chord tones (from the root the nearest members below are the fifth and the third, not another third), and is called for **both hands** once the grade declares a `maxNotesTotal` (Grade 5, the "four-part, two notes per hand" texture) rather than the left hand only.

Two limits are enforced live: `maxNotesPerChord` per hand, and `maxNotesTotal` across both — the latter needs `against` (the other hand's timeline) to know what is already sounding. Chord thickness is drawn per chord (`want`, mostly the minimum) rather than always taking the grade's maximum, which is a ceiling the syllabus permits occasionally, not a target; taking it every time produced six three-note chords in a seven-note bar. Stacked notes also need the **vertical clash check against the other hand**, not just the ceiling — in a split bar the hands can be on different chords, and in minor one can hold the raised 7th against the other's natural.

`harmoniseLeadingNotes` must reconcile **chord notes as well as main notes** (`leadingNoteVoices`), or a stacked leading note in one hand sounds against the natural 7th in the other — a false relation. That hole only opened once both hands could carry chords.

The per-grade audit worth re-running after touching any of this: notes/bar, span, chord depth and simultaneous-attack counts should all rise monotonically with grade and land on the rules table's declared limits.

### Grade 6-8 extras

Grade 6-8 tests do **not** print a piece title above the tempo/character word (an earlier `TITLES`-pool design was dropped per request) — the heading is just the tempo/character word, same as every other grade.

`applyExpression` implements the rules table's long-documented-but-unbuilt pedal/ornament/tempo-change features: `addPedalMarking` (gated on the rules table mentioning pedal — English "pedal" at Grade 5, Chinese "踏板" at Grade 6-8, gate checks both), `addMidPieceTempoChange` (rit./a tempo pair around the halfway bar, `grade >= 6`), and `addOrnaments` (step-wise acciaccatura on 1-2 melody notes, `grade >= 7`). A grace note is `event.grace = {pitch}` on the note it decorates, not a separate event — MusicXML forbids `<duration>` on a grace note, so `musicxml.js`'s `renderGraceNote` emits it as its own `<note><grace slash="yes"/>...</note>` immediately before the main note.

`addPedalMarking` places a bracket pedal line over a 2-4 bar span. A plain start/stop pair would hold straight through whatever chord changes happen underneath, smearing unrelated harmonies together — no real pedalling does that. It walks the span and drops a `<pedal type="change"/>` (lift-and-immediately-redepress notch) at every bar where the sounding chord actually changes, including *inside* a split bar (see below), using a plain `stop` only at the very end.

**Grade 6's "偶爾出現短暫換譜號" and Grade 7's "左手上行進入高音譜號" were declared in the rules table's `otherFeatures` but had no implementation anywhere** — the same "declared feature never appears" fault the audit's `expression` section exists to catch, just never extended to check clef changes (or, at the time, to Grade 8's modulation/chromaticism/cross-staff writing — see below). `addClefChanges` (`generate.js`) fixes Grade 6/7: a hand's line occasionally sits persistently in the *other* staff's comfortable register — the melody arch pulling the right hand down toward the bottom of its window, or an accompaniment figure carrying the left hand up toward the top of its own — and real engraving switches that staff's clef for the span rather than stacking ledger lines. This is a pure post-hoc rendering decision keyed off pitches the ordinary window/arch machinery already produced (`buildStaff`, `assignPitches` — neither touched by this), not a forced detour into the other register, which is exactly why it reads as "occasionally" rather than every test: it only fires where a bar's *every* sounding pitch (`event.pitch` **and** any `event.chord` stack — missing the stack was a real bug caught while calibrating this, since a chord's lower tones are exactly what a melody-only check would miss) already crosses the threshold (≤G3/staff 1, ≥B3/staff 2) for a contiguous 1-4 bar span, excluding the first and last bar. Measured (800 tests/grade): Grade 6 10.4%, Grade 7 16.8%, Grades 1-5 and 8 correctly 0% (the gate checks `otherFeatures` for `換譜號`/`譜號變換`, which only Grade 6/7 declare). `musicxml.js` emits it as a genuine mid-piece `<attributes><clef>` block — a structurally different element from the `<direction>`-based marks (dynamics/wedge/pedal/words) `bar.directions` already carries, so it's stored as `bar.clefChange = {sign, line}` instead and rendered immediately before that staff's notes in the bar where it takes effect. `test/musicxml.test.js`'s "attributes and clefs are declared once..." had to be rewritten to re-derive its expected `<attributes>`/`<clef>` counts from `score`'s `clefChange` markers rather than hard-coding "exactly one" — the hard-coded version predates this feature and started failing (correctly) the moment a real mid-piece change existed to count.

**Grade 8's "半音音群" had the same problem — declared, unimplemented — plus a dead parameter that made it look half-built:** `theory.js`'s `pitchAt` already accepted a `chromaticAlter` option (raises/lowers a pitch a further semitone on top of the key signature, independent of `raiseSeventh`), but nothing in the whole codebase ever passed it. `addChromaticGroup` (`generate.js`) fixes it: a brief chromatic scalar run filling a melodic major third in the right hand, e.g. C-C#-D-D#-E in place of a plain leap from C to E, decorative and melody-only like `addOrnaments`' grace notes (same precedent for not clash-checking it against the other hand — a passing chromatic figure is not a harmony event). Only a *major* third (4 semitones) whose passed-through diatonic degree splits it into two clean whole tones is filled, deliberately conservative rather than attempting every third: a minor third doesn't divide evenly into equal chromatic steps without a triplet, and an uneven diatonic split (a semitone plus a tone, which happens near some scale degrees) would put the middle passing note off the true chromatic midpoint. Filtering to the clean case keeps every note built from `pitchAt`'s `chromaticAlter`, so the spelling is always the *next* scale degree's accidental (C#, D#) rather than a stacked double-sharp on one letter. Three real bugs surfaced calibrating this against the existing test suite, not against an isolated example:
  - **A dotted quarter note passed the `type === 'quarter'` filter but isn't a quarter's duration** — `dur/4` on a dotted quarter (1.5× a plain one) produced a 16th note 1.5× too long, caught by "printed note values match their durations" (expected 6, got 9). Fixed by also requiring `dots === 0`.
  - **A quarter note that starts off a clean beat boundary** (e.g. the second half of a syncopated cell) split into four 16ths that straddle two beats, and `computeBeams` correctly refused to beam them as one group — caught by "beams never cross a beat boundary". Fixed by requiring the candidate's own offset within the bar to be an exact multiple of `bar.beatDuration`.
  - **The new events had no `raiseSeventh` field**, which every other pitch-assignment path in `melody.js` sets (`degreeOf(dstep, key) === 6`) and `harmoniseRepeatedLeadingNotes`'s own invariant test checks on every immediately-repeated same-dstep pair — an unset field reads as a disagreement even between two otherwise-identical notes, caught by "a repeated note never disagrees with itself on the raised 7th". Fixed by computing it the same way every other event does.
  Measured (2000 tests, stress-tested past the unit tests' four fixed seeds): 20.6% of Grade 8 tests, zero errors; audited at 19.8% across 1000 Monte-Carlo runs, all other grades correctly 0%.

**Grade 8's "曲中轉調" (mid-piece modulation) was the last of the four declared-but-unbuilt Grade 8/6/7 features, and the riskiest — it touches the key system every other pass in the pipeline assumes is fixed for the whole piece.** `addModulation` (`generate.js`) sidesteps that risk entirely rather than confronting it: it does **not** generate a second phrase in a second key. The whole piece is built once, by the completely unmodified pipeline, in one key — then the consequent phrase (from `halfCadenceBar` onward, the same split point the period structure already uses) is rigidly transposed a perfect fifth (+4 diatonic steps) into the dominant major key. Transposition is what makes this safe: it does not change any note's relationship to any other note — its interval against the other hand, its role in its own chord, its distance from a neighbour — only its absolute level and notated spelling, so every invariant already checked for that span (no clash, no parallel motion, correct cadence shape) survives for free. `progression`'s roman numerals need no change either, since they were already key-relative: a transposed ii-V-I still reads as ii-V-I in the new key. Scope is deliberately narrow for a first real implementation — major-key pieces only (a minor piece's most natural modulation, to the relative major, shares the outgoing key's signature and so prints no visible change, a weaker fit for a feature about *reading* a key change) — and mutually exclusive with `addChromaticGroup` on one test, since that pass reads `score.key` directly and a candidate landing in an already-modulated span would be spelled against the wrong key. Four real bugs surfaced building this, none visible from reasoning about an isolated example:
  - **A transposed note can walk past the grade's declared range even though the untransposed original never did** — shifting a phrase that was already sitting near the top of its window up a further fifth pushed real notes past `rules.range[hand].maxMidi`, caught by "pitches stay inside the grade range for each hand". Fixed with a dry run: every transposed pitch is checked against the grade's range *before* anything is mutated, and the whole modulation is abandoned (not partially applied) if any note would land outside it.
  - **The new tonic's letter name is fixed by the fifth (always 4 diatonic letters up), but its accidental is not** — spelling it as a bare letter (`LETTERS[...]`, no `#`/`b`) produced a tonic a semitone flat of the real one for any outgoing key whose dominant needs an accidental (e.g. Gb major's dominant is Db, not D), caught by comparing the actual final pitch class against the expected one across thousands of seeds — the 4 fixed seeds the unit tests use never happened to hit this case. Fixed by deriving the new tonic's spelling from `pitchAt` on the *original* key's own fifth degree (which already knows Gb major's 5th is Db), matching how every other `key.tonic` string in this codebase is written.
  - **Two existing tests assumed a test always cadences in, and prints accidentals against, its one opening key** — both correctly failed the moment a real modulating test existed to violate that assumption ("every test cadences on the tonic", "printed accidentals agree with the key signature"). Neither was wrong to have existed; both needed to learn about `score.keyChange` — the cadence check now compares against the destination key when one exists, and the accidental check now splits the MusicXML by measure and switches which key signature it judges each one against at `score.keyChange.barIndex`, the same real thing the renderer itself has to do.
  - **The audit's own "final bass note is the tonic" check had the identical blind spot**, sitting at a precariously borderline 95.3% (threshold ≥95%) purely from a handful of modulating Grade 8 tests being marked wrong for correctly cadencing in their new key — a spurious near-failure waiting to happen on a different random seed. Fixed the same way as the unit test; re-measured at a clean 100%.
  Measured across 3000 stress-tested seeds (well past the unit tests' four fixed ones): 4.7% of Grade 8 tests modulate, zero errors — genuinely rarer than the other three Grade 8/6/7 features, and honestly so: the range-safety dry run above rejects the large majority of otherwise-eligible candidates, since a Grade 8 piece's melody frequently already sits close enough to its declared ceiling that transposing up a further fifth would exceed it. That is a real physical constraint of the grade's own range table, not a bug to paper over by loosening the check.

**Grade 8's "跨譜表寫作" (cross-staff writing) was the fourth and last of the declared-but-unbuilt Grade 6/7/8 features.** `addCrossStaffWriting` (`generate.js`) is the same underlying idea as `addClefChanges` (a hand's note sitting in the *other* staff's comfortable register) but for a reach too brief — one isolated note, not a multi-bar span — to justify changing the whole staff's clef: real engraving instead prints just that note on the other staff. The two never overlap in practice (`addClefChanges` only runs for Grade 6/7, this only for Grade 8), so no exclusivity guard was needed the way modulation/chromatic-group required. Candidates are restricted to a plain, undecorated single note (no chord stack, grace, slur or articulation to orphan), of a note value that is never beamed (quarter or longer — a beamed eighth/16th crossed alone would leave its beam partners stranded on the original staff), isolated from its own hand's neighbours (the notes immediately either side must stay in the normal register, or this is the sustained case `addClefChanges` handles, not a brief one), and clear of whatever the target staff is actually sounding at that instant (built from `soundingTimeline`, the same helper `stackChordTones` already uses for its own clash check) — the whole point of crossing there is that it is free. `musicxml.js` renders it by overriding just that event's `<staff>` to the target staff and giving it a reserved voice number (5, unused by either staff's own voice 1/2) rather than moving it in the event sequence — `<staff>`/`<voice>` are pure placement metadata in MusicXML, so this doesn't touch either staff's own `<backup>` duration bookkeeping, and playback is unaffected for the same reason (`playback.js` reads `pitch`/timing off the event directly, never `crossStaff`, so the note still plays as its own hand's note at its own time — only where it's drawn changes). Measured (3000 stress-tested seeds): 10.5% of Grade 8 tests, zero errors, all other grades correctly 0%.

With all four Grade 6/7/8 features now real (clef changes, chromatic groups, modulation, cross-staff writing), Grade 8 finally reads as harmonically and notationally more advanced than Grade 7 rather than differing mainly in range/density — the gap this whole investigation started from.

### Two chords in one bar

`buildProgression` (`harmony.js`) can split a middle bar (never the opening I or the V–I cadence) into two chords occupying even halves of the bar, gated by `twoChordBarChance` (`generate.js` passes `grade >= 5 ? 0.3 : 0`). A split entry is `[first, second]` instead of a plain roman numeral; `firstChord`/`lastChord` unwrap either shape to the chord at the bar's start/end, and `chordAt(entry, offset, barDuration)` returns whichever half sounds at a given offset — `melody.js`'s `assignPitches`/`stackChordTones` call it once per event (not once per bar). `addPedalMarking` uses `firstChord`/`lastChord` for bar-boundary comparisons, and `addMidBarPedalChange` drops a `change` mark partway through any split bar in the pedal's span, at the first event starting at/after the bar's halfway point. That mark can't go at the front of `bar.directions` like every other direction — it has to land between two specific notes — so directions gained an `atEventIndex` field (default 0), and `musicxml.js`'s `renderBar` interleaves each direction immediately before the note at that index as it walks the bar.

### Rules table is the single source of truth

`src/rules/abrsm-piano-grades.json` drives every grade-specific parameter: keys, time signatures, bar-count ranges, rhythm vocabulary, hand range/tessitura, texture (five-finger position, hands-together, chord stacking), dynamics, articulations, tempo terms. Each grade carries a `confidence` marker (`verified`/`partial`/`inferred`), surfaced to the user in the UI whenever it isn't `verified`. Changing generation behavior for a specific grade should almost always mean editing this JSON rather than the generator code. `docs/abrsm-sight-reading-analysis.md` and `docs/abrsm-sight-reading-knowledge-base.md` are the source analysis behind the table's numbers.

### Frontend (`src/app/`)

- `app.js` — orchestrates everything: loads the rules JSON, initializes OSMD, wires the generate/prepare/play/stop buttons, runs the 30-second preparation countdown, and auto-fits layout (`fitScore`). `startCountdown` gives the tonic triad (`tonicTriadMidis`, built from `theory.js`'s diatonic-step spelling so the chord follows the test's actual key) and only starts the visible 30-second timer once it finishes ringing — matching an ABRSM examiner giving the key before preparation time actually begins, rather than the two starting together. `fitScore` also sizes the score to the screen: `availableScoreHeight()` is the room from the top of the engraving to the bottom of the window, and the height is read from the **rendered SVG** (`renderedScoreHeight`), not the bar boxes — pedal brackets, hairpins and slurs hang outside the staves and are exactly what would otherwise be cut off. The height constraint applies only in the pass that asks for it: folding it into every candidate drove a phone, where nothing fits, to the zoom floor and made the whole page tiny. `ensureFitsHeight` is the last word, and checks first whether the floor would fit at all — so a tablet comes down the little it needs to and a phone is left alone to scroll. It also reverts if shrinking strands a bar on a line of its own, which re-flowing the unforced layout can do.
  - **The tempo/character-word text is pinned to a fixed spot after every render (`pinTempoTermPosition`), not left where OSMD puts it.** OSMD centres that direction on whichever event starts bar 1 — an ordinary first note sits right at the start of the measure, but a whole-bar rest (Grade 1's alternating hands, when the right hand sits out bar 1) is drawn centred within the measure by VexFlow, so the same term ended up in a visibly different spot depending on which hand opened, even though both are "beat 1" of the piece. `pinTempoTermPosition` runs after every `osmd.render()` call (wrapped once at construction, so all nine call sites across `fitScore`'s search get it for free) and moves the term's `<text>` element to sit right after bar 1 staff 1's clef/key/time signature, using the gap OSMD already left before the time signature as the margin so it scales with zoom instead of a fixed pixel value.

`fitScore` picks bars-per-line in two passes: **first a count that divides the bars evenly** (largest first, down to 3), then — only if none of those renders at `zoom >= MIN_ZOOM` without stranding a lone bar — the most compact count that at least avoids a lone bar, and finally the natural wrap. The even pass matters because bars-per-line has to divide evenly for every *line* to come out the same width in the first place: six bars at four per line gives 4+2, and even with `stretchLastSystemLine` on (below) a two-bar line is stretched across bars that don't need it, reading as oversized rather than merely aligned. `MAX_MEASURES_PER_LINE` is 5 rather than 4 so a ten-bar test (no even divisor at four or below) can split 5+5 instead of 4+4+2; on a narrow screen the zoom floor rejects it and the search falls through. The `resize` listener that triggers `fitScore` filters to actual width changes only — mobile Safari fires `resize` on address-bar show/hide during ordinary scrolling (only `innerHeight` changes), and refitting on that reset scroll position.

**Bar numbers used to print on more than just each line's first bar.** OSMD's default numbers a bar at the start of every system *and* periodically on a fixed interval regardless of line breaks — with `fitScore` forcing a uniform bars-per-line count, that interval routinely landed on a bar mid-line too (bar 3 of a 3-bars-per-line test, printed a number nothing but a line's first bar should carry — real engraving, and every other bar-count convention this app follows, numbers a line by its first bar only). Fixed with the `drawMeasureNumbersOnlyAtSystemStart: true` constructor option.

**Lines with the same bar count used to end at different points**, because OSMD's default behaviour leaves the *last* system of a piece at its own natural (unjustified) width — normal single-document typesetting convention, but it meant a test whose final line happened to have the same bar count as an earlier one still didn't line up with it on the right edge, reading as sloppy rather than deliberate. `stretchLastSystemLine: true` (an OSMD constructor option) fixes this — every system, including the last, is now justified to the same frame width. Bar-to-bar width still isn't perfectly uniform (a bar's own note density still asks for its fair share of that shared width), but `osmd.EngravingRules.FixedMeasureWidth = true` visibly reduces that: without it, the same-shaped bar across different lines could differ by 50+ px purely from how that line's *own* leftover space happened to distribute; with it, corresponding bars across lines converge on close to the same width because each measure's width is driven mainly by its own content rather than by how much slack its particular line needed to fill.

**Two tests of the same shape (grade, bar count) used to be able to render at visibly different sizes**, because `fitScore`'s search is driven entirely by *measuring the rendered content* — how wide a bar comes out depends on note density, chord thickness, accidentals, dynamics — with nothing tying the outcome to anything about the test other than what happened to fit. `layoutCache` (persisted to `localStorage`, keyed by `layoutShapeKey`) fixes this: the first test of a given shape runs the full search as before and the winning `measuresPerLine`/`zoom` become that shape's canonical layout; every later same-shaped test applies the cached layout directly and skips the search. `matchesRequestedLayout` (below) is what makes the two axes below safe to fold into the key at all: a shape that no longer actually fits (a wider metre, a narrower viewport) gets caught and re-searched rather than silently rendered wrong.
  - Exact time signature is deliberately not part of the key — a Grade 1 four-bar test should read the same size whether it's in 2/4, 3/4 or 4/4, the way a printed sight-reading book keeps one page layout per test length rather than resizing by metre. But time signature isn't dropped outright either: it's bucketed by how many quarter notes' worth of content a bar actually holds — `narrow` at four or under (2/4, 3/4, 4/4, 2/2, 3/8, 5/8, 6/8, 7/8) versus `wide` above that (9/8, 5/4, 12/8, 7/4) — since a 2/4 test and a 12/8 test of the same bar count genuinely don't need the same amount of room, while 2/2 and 3/8 hold no more content than a 4/4 bar despite not being in the classic 2/4-3/4-4/4 family and don't deserve to be bucketed with 12/8 either. Conflating metres of noticeably different width into one shared canonical zoom meant whichever metre established the cache first either left the other one needlessly small or got re-searched on every single render, never settling into the fast path.
  - Viewport width is bucketed into the key too (`layoutWidthClass`: phone / compact / medium / wide), because a canonical size established on a narrow phone has no business constraining a desktop that has room for more bars per line and a larger zoom — reusing the phone's cramped answer would waste that space for no reason a reader on a wide screen could point to. The tiers are coarse rather than the exact pixel width so minor viewport differences (two different phone models, say) still converge on one shared layout instead of each device getting its own.
  - **The cache alone did not actually make same-shaped tests match each other.** A denser test that didn't fit the cached zoom shrank further via `shrinkUntilNoSingleBarLines`/`ensureFitsHeight` — correctly, it never overflowed — but that shrink amount was thrown away instead of written back, so the *next* same-shaped test started over from the original (larger) cached zoom and shrank by whatever amount its own content needed, independently. Generating three dozen same-shaped Grade 6 tests turned up the same "4/4, 12 bars" shape rendering at three different zoom levels (0.659, then 0.606, then 0.558 — each exactly one more 0.92 shrink step than the last), which is the literal "same grade, same bar count, different size" bug report this was meant to prevent in the first place. Fixed by ratcheting `layoutCache[shapeKey]` down whenever a same-shaped render needs a smaller zoom than what's cached, rather than discarding that shrink — every later same-shaped test (including less-dense ones that would have fit the old, larger cached zoom) then converges on that one shared, tighter size. The ratchet only ever shrinks the cached value, so nothing that fit at the old cached zoom can start overflowing.
  - **The cache could still disagree with itself on the number of lines, not just the zoom.** `RenderXMeasuresPerLineAkaSystem=n` is a target OSMD is free to ignore: when `n` bars don't actually fit the container at the current zoom, OSMD silently re-wraps into a *different* system shape instead of honouring `n` — e.g. "3 per line" on a 6-bar test can come back as three systems of 2 rather than the requested two systems of 3. `hasSingleBarLine` only catches a re-wrap that still strands a lone bar; a re-wrap into some *other* uniform shape sails right through it and reads as a success, so two same-shaped tests could each request the same `n`, each get silently re-wrapped to a *different* actual shape depending on their own content, and both still get cached under that same `n` as if they'd rendered identically — a real user report ("Grade 1, 4 bars" rendering as one line of 4 for one test and two lines of 2 for another) traced back to exactly this: a fresh, uncached search for a *sparse* four-bar test let OSMD honour `n=4` as one true line, while a denser test of the same shape silently re-wrapped that same `n=4` into two lines of 2 — both cached under `measuresPerLine: 4`, both "valid" by the stranding check alone, but visibly different layouts. Fixed with `matchesRequestedLayout`, which checks that every system actually has exactly `n` bars (barring a legitimate remainder on the last) before a candidate is accepted in the initial search, and re-checks it against the cached `n` on every cache hit too — a cache entry that no longer matches for this test's content is treated as stale and falls through to a fresh, freshly-verified search rather than being trusted. Confirmed by generating the same "Grade 1, 3/4, 4 bars" shape from twelve independent fresh sessions (no shared cache): before the fix, `measuresPerLine` and the actual line count varied per session; after, every session converged on the same two-lines-of-two structure, with only the zoom (handled by the ratchet above) differing slightly by session.
  - Fixing the mismatch check surfaced a second, older bug it depended on: the search's first pass unconditionally excluded `n=2` (`n >= 3`) to avoid over-fragmenting long pieces (a ten-bar test at two-per-line is five lines), but the *second* pass then also skipped `n=2` for any bar count where it divided evenly, under the mistaken belief it had "already been tried above" — it hadn't, since the first pass never went below 3. For a short, evenly-divisible test (a Grade 1 four- or six-bar piece) this meant `n=2` was never genuinely attempted by either pass, so once `matchesRequestedLayout` started correctly rejecting `n`'s that OSMD silently re-wrapped, a four-bar test with no other divisor to fall back on could exhaust every candidate and drop to the unforced natural wrap for no reason — exactly the shape that most needs `n=2` to be a real option. Fixed by lowering the first pass's floor to `n >= 2`; because the loop still tries larger counts first and only reaches `n=2` once everything bigger has failed, this doesn't reintroduce the over-fragmentation the original floor was guarding against.
- `stage.js` — reading-stage geometry. Reads bar/system bounding boxes directly out of the rendered SVG (`g.vf-measure`, `g.staffline`) rather than OSMD's internal graphic model, and drives the playback highlight box, moving playhead, and auto-scroll-to-system.
- `playback.js` — reference audio playback matching a sibling app's ("ScrollScore") audio chain: real Salamander piano samples, pitch-shifted to the nearest recorded note → gain envelope → stereo pan by pitch → reverb send (synthesized IR) → limiter → output. Falls back to a synthesized oscillator tone if the samples can't be fetched. `playChord` (the tonic triad given before the 30-second preparation, matching an ABRSM examiner's keynote) reuses this same chain and the `voices`/`stopTimer` bookkeeping `play()` uses — not a second audio path — so Stop or a new test cuts it off exactly as it would the reference playback. It leaves `startTime` untouched, since a keynote isn't the timeline `startFollowing()` tracks.
  - **Articulation used to reach the score but not the speaker.** `generate.js` wrote `staccato`/`accent` (and, since fixed, `tenuto`/`staccatissimo`/`strong-accent`) into `event.articulations` and `musicxml.js` serialized them, but `play()` handed every note's full written duration straight to the sample/oscillator regardless — so staccato and legato were audibly identical, a fact only a human listening could catch (nothing in `npm test`/`npm run audit` renders sound). Fixed by porting ScrollScore's own `applyArticulation`: `sustain` is carved out of the note's own duration (staccatissimo 0.25×, staccato 0.35×, tenuto forced to ≥0.98×) while the *next* note's onset is untouched, so the gap left behind is what makes detachment audible; accent/`strong-accent` scale peak gain instead (1.3×/1.5×). `legato` is derived from `event.slur` spans — `layOutStaff` collects each slur's `{start, end}` in one pass (a slur only marks its first and last note, so the first note can't know its own span's end until the matching `stop` is reached) and a legato note is left to ring into the next note's attack (`LEGATO_TAIL`, longer than the default release) rather than cut clean.
  - **Staccato still barely read as detached even once `sustain` was shortened, because `tail` — the release ramp after `sustain` ends, `TAIL` = 0.4s by default — never shrank with it.** ScrollScore's own `applyArticulation` doesn't shrink `tail` for staccato either, so this is a deliberate departure from a literal port, not an oversight: at an ordinary tempo an eighth note is only 0.2-0.3s from the next one, so a shortened `sustain` plus 0.4s of release (plus the reverb send, which follows the same envelope) still bleeds well past the next note's onset — the shortening was real but too small relative to the fixed tail to read as silence before the next attack. ScrollScore's own pizzicato guitar technique already caps `tail` at 0.12s for the same underlying reason (a damped, short note needs a short *release*, not just a short sustain); `applyArticulation` now applies that same cap to staccato (0.15s) and staccatissimo (0.12s).
  - **`staccato`'s 0.5× sustain was the textbook "half the written value" rule, not how it actually gets played.** A real pianist cuts a staccato note noticeably shorter than half, especially in a light/quick sight-reading piece — the user's own ear on it, comparing against real playing rather than theory. Narrowed to 0.35× (tail correspondingly from 0.2s to 0.15s) while keeping a clear gap above staccatissimo's 0.25×/0.12s, so the two marks stay audibly distinct from each other rather than converging.
  - **`tenuto`/`staccatissimo`/`marcato` were declared per grade in the rules table but `applyExpression` never wrote them** — the same "declared feature never appears" bug the audit's `expression` section exists to catch, just never extended to check these three. Now generated alongside `staccato`/`accent` (gated on `rules.articulations`, same as everything else there), and the audit checks them too. MusicXML's tag for what the rules table calls `marcato` is `<strong-accent/>`, so that's the literal string in `event.articulations` — the array is written straight through as tag names (`<${articulation}/>` in `musicxml.js`), so a mismatched label would either serialize garbage or silently fail to match in playback.
  - **Dynamics, wedges, pedal and rit./a tempo were engraved but silent too** — `play()` read only pitch and written duration off `bar.events`; every `bar.directions` entry (`dynamics`, `wedge`, `pedal`, `words`) was ignored outright, so a test marked `pp` played exactly as loud as one marked `ff`, a crescendo had no ramp, pedalled notes decayed like any other, and a mid-piece `rit. … a tempo` had no effect on tempo at all. `play()`'s per-staff loop was rebuilt around `scoreDirectionTimeline` — every direction from *both* staves, in one notated-offset-ordered list, since a marking is only ever written to whichever hand `applyExpression`/`addPedalMarking` happened to attach it to but is meant to govern the whole texture:
    - `buildDynamicsEnvelope` turns each `dynamics` mark into a gain step (`DYNAMIC_GAIN`, `mf` left at the old fixed loudness so unmarked tests are unchanged) and ramps a `wedge`'s span linearly toward whichever dynamic follows it, rather than snapping at the wedge's `stop`.
    - `buildPedalRanges` merges a pedal's `start`/`change`/`stop` notches into one continuous span — the mid-span `change` marks a lift-and-redepress for the *engraving* only, the pedal is never actually up in between — and a note attacking inside it gets a longer, slightly louder tail (`PEDAL_TAIL`/`PEDAL_GAIN_BOOST`) than a plain release, standing in for the un-damped strings' resonance without going as far as literally re-sustaining every note through the harmony change.
    - `buildTimeMap` replaces the flat `secondsPerDivision` multiply with a numerically-integrated tempo curve (`tempoScaleFn`, trapezoidal rule at sixteenth-note steps): a `rit.` ramps the tempo down toward the following `a tempo` (or the piece's end, for a closing `rall.` with nothing to restore it), so every later note in *either* hand — not just the ones in the marked bars — both starts later and lasts longer, which is what actually reads as slowing down rather than a label with no acoustic effect. `layOutStaff` now works in notated-offset (division) space rather than seconds for exactly this reason: real timing only exists once `buildTimeMap` has been built from the *whole* piece's directions, so a single staff's layout can't resolve it alone.
    - Grace-note ornaments (`event.grace`) were visually rendered but never scheduled as sound at all; `play()` now schedules the crushed note itself, `GRACE_LEAD` seconds before the main note's own onset rather than stealing time from the beat.
  - **The whole chain was quiet compared to normal web audio.** `master.gain.value` had only ever been set for headroom (0.48, chosen so Web Audio summing several simultaneous voices/reverb send wouldn't clip) — never calibrated against any actual loudness target, so the rendered playback sat well under what a listener expects from a normal web page, let alone YouTube/Spotify's -14 LUFS integrated normalization target (the standard the user asked to be matched against — "根據一般網頁的LUFS （甚至是YouTube規範的）"). `scripts/loudness.js` (new) measures the real production chain's output loudness directly rather than reasoning about the gain math in the abstract: it drives the actual app through Playwright, taps `window.__playback.audioNodes` (a new debug hook on `playback.js`'s returned player object, `{context, master, limiter, output}`, matching the existing `window.__osmd`/`window.__stage` convention) at `output` — the exact signal that reaches `context.destination` — and runs it through a real ITU-R BS.1770-4 K-weighting filter (two-stage IIR, bilinear-transformed to the browser's actual `context.sampleRate` rather than hardcoded 48kHz coefficients) with the spec's absolute (-70 LUFS) and relative (-10 LU) gating. The real Salamander samples are blocked from this environment's egress (`tonejs.github.io`, see below), so sample requests are intercepted (`page.route`) and fulfilled with a synthesized decaying-harmonic tone instead — close enough in envelope/crest-factor for calibrating the downstream gain stage, since everything from the sample buffer onward (envelope, master gain, limiter, safety clip, reverb) is the real unmodified code path. Measured baseline across all 8 grades: -23.05 LUFS average (individually -15 to -18 LUFS for the sparser early grades, down to -11 LUFS for the busier later ones) — 9dB under target. `master.gain.value` raised 0.48 → 1.36 (that +9dB correction, `10^(9/20)`); re-measured post-change at -13.28 LUFS average (range -18.23 to -10.70 across grades), within a semitone-scale <1dB of -14 LUFS.
  - **"Peaks confirmed safe" the first time around only checked sample peak, not true peak, and one was not the other.** Asked directly whether true-peak safety had actually been verified, the honest answer was no — `scripts/loudness.js` only tracked the raw discrete sample values' max absolute value, which is not what ITU-R BS.1770-4/EBU R128 mean by true peak: a DAC reconstructs a *continuous* waveform between samples, and that reconstruction can overshoot any individual sample's value, especially for a signal a limiter has already pushed close to 0dBFS — precisely this app's post-limiter output. Added a real 4x-oversampled true-peak measurement (`measureTruePeak` in `scripts/loudness.js`): the tapped raw waveform is handed to an `OfflineAudioContext` rendering at 4x the sample rate, letting Web Audio's own bandlimited resampler do the reconstruction (not a naive linear interpolation) before re-checking the peak on the oversampled result. It found a real problem: one randomly-generated Grade 8 test measured **0.00 dBTP — literal digital full scale** — despite the compressor's -3dB threshold, because `DynamicsCompressorNode` has no lookahead. Several notes attacking on the same sample (an ordinary chord, which is exactly what Grade 8's texture writes routinely) sum and reach the output before the gain-reduction envelope has had time to respond; the compressor only starts pulling the level down *after* the transient has already gone out at whatever level the chord summed to. Fixed with a second stage after the compressor: a `WaveShaperNode` (`oversample: '4x'`, so the shaping itself doesn't reintroduce the exact problem it exists to prevent) applying a scaled-tanh soft-clip curve (`TRUE_PEAK_CEILING * tanh(x / TRUE_PEAK_CEILING)`, `TRUE_PEAK_CEILING = 0.891` ≈ -1dBTP, the streaming-safe ceiling YouTube/Spotify both target) — near-identity for anything well under the ceiling, so it's inaudible on ordinary passages, and asymptotically approaches but never crosses the ceiling for whatever rare transient the compressor let through. The compressor's own threshold was also tightened -3dB → -6dB, so the soft-clip is a safety net doing occasional light work rather than the primary gain-reduction stage. Re-measured (multiple trials per grade, since the fault was already known to depend on which random chord landed where): worst observed true peak across all 8 grades is -3.23 dBTP (Grade 8) — every trial lands 2+ dB inside the -1dBTP ceiling, a large margin from the 0.00 dBTP the fix replaced.
  - The `output` debug-hook node (the true-peak safety clip, not the bare compressor) is what any future measurement or listening tooling should tap — `limiter` is still exposed on the same object for anything that specifically wants the pre-safety-net signal, but it is no longer the node that reaches `context.destination`.
  - Real-recording timbre could shift the exact LUFS/true-peak numbers slightly from what the synthesized proxy measured; a listening spot-check on the deployed site is worth doing if playback still sounds under- or over-loud, or if the chord-heavy passages ever sound audibly squashed (a sign the safety clip is engaging more than the rare-edge-case role it's meant for).

The whole test always renders in normal page flow — no fullscreen mode, no cropped follow-window. There is deliberately **no fullscreen toggle**: the title bar, the meta strip and the score are the entire page, so a distraction-free view would have nothing left to strip away. (An earlier design put the transport in a separate row that hid with the title bar in fullscreen; that whole mechanism — `.statusbar`, `.pseudo-fullscreen`, the double-tap gesture — was removed once the layout below made it redundant, rather than kept as dead weight.)

The transport controls (`generate/prepare/play/stop`) live in `.topbar` itself, right-aligned opposite the title via `.topbar`'s `justify-content: space-between` — the same single row at every width, never rearranged. Because the controls have no sibling that reacts to test state, **generating a new test cannot move them**: only `#meta` (the key/time/bar-count/tempo strip, directly below the topbar) and the score change. Below 680px the buttons drop to icons (`.btn-label` hidden) to keep the row from overflowing next to the title.

`#meta` and `#countdown` both start `hidden` and are revealed together in `newTest()`, once there is a test to describe. The countdown moved out of the meta strip and into `.score-frame`'s own top-right corner (`.countdown`, `position: absolute`), mirroring `.grade-select` at the top-left — both read as "controls for this sheet of paper," symmetric corners of the score rather than page-level chrome. `.score-frame`'s extra top padding reserves room for both without overlapping the first system.

**At 1024px and up — or a phone rotated to landscape — the grade selector and countdown leave the score's corners and join the meta line in one row instead** (`TOP_ROW_QUERY`, `pinTopRowLayout` in `app.js`) — a portrait phone or held tablet doesn't have room to spare, so pinning them to the paper's corners is the better use of the width there, but a screen that qualifies just gets a stretch of near-empty space under the meta line where `.score-frame`'s corner-reserving top padding used to sit. Landscape phones qualify too (`(orientation: landscape) and (max-height: 500px) and (min-width: 680px)`, alongside the outright `min-width: 1024px` case) — an iPhone Pro sideways is 852px wide, plenty for the combined row, but only 393px tall, and the separate rows the pinned-corner layout costs are exactly the vertical space landscape has least of; the height/width guards keep this off a portrait phone or tablet (which has height to spare) and off a landscape phone too narrow to lay the row out even sideways. `pinTopRowLayout` moves the actual `#grade`/`#countdown` elements (not copies — they keep their ids and listeners either way) into `#meta-row`, a wrapper around `#meta` added specifically so they have a stable home to be moved into: `showMeta()` replaces `#meta`'s own innerHTML on every test, which would silently delete anything appended directly inside `#meta` itself. Called once at `init()` and again on every `TOP_ROW_QUERY` breakpoint crossing (a `matchMedia` listener, not the width-diffing `resize` listener that drives `fitScore` — a discrete layout swap needs its own precise trigger), followed by `fitScore()` since `.score-frame`'s top padding differs between the two arrangements and the available height has to be measured fresh. `.meta-row` is a deliberate no-op below the breakpoint — narrower viewports keep `#meta`'s own margin doing the "space below the topbar" job exactly as before, so nothing about the pinned-corner layout changed. The combined row's structural rules (`.meta-row`'s flex layout, `position: static` on the grade selector/countdown, `.score-frame`'s reclaimed top padding) apply under both qualifying conditions, but *font sizes* stay purely width-tiered: true desktop gets its own sizing (`.meta-row .meta span`, `.grade-select`, `.countdown`, gated on `min-width: 1024px` specifically) while a landscape phone — still 561–1024px wide — just inherits the tablet band's sizing below rather than needing a third, near-duplicate set of numbers. `scripts/devices.js`'s `gradeInsideScoreFrame`/`countdownInsideScoreFrame` checks call the exact same `matchMedia` string (not a re-derived width check) so the two can't quietly drift apart — they had assumed the corner-pinned layout unconditionally and flagged the new arrangement as elements having "drifted off the score frame's corners" until fixed.

**The 561-1024px tablet band gets its own font-size bump too** (`.btn`, `.grade-select`, `.meta span`, `.countdown`, inside the existing `@media (min-width: 561px) and (max-width: 1024px)` block) — a tablet is normally read from further away than a phone held in the hand, closer to a desktop's viewing distance, so reusing the phone-tuned base sizes there read smaller than the room available actually calls for, even though there isn't width yet for the 1024px+ combined row. `.meta-key`/`.meta-time`/`.meta-bars` get matching wider columns in the same block — the fixed-width column trick only avoids shifting the "丨" separators if the column is wide enough for the *new* font size's widest string, and enlarging the text without re-measuring the column would silently overflow it. `.btn.icon-only`'s width is set explicitly in this block too, or it would inherit the plain `.btn` rule's width from the 680px icon-only breakpoint (which overlaps the bottom of this range) while this block's own height bump still applied, leaving icon buttons taller than they are wide.

`.topbar` and `.score-frame` are styled after ScrollScore directly: no rounded corners, no drop shadow, no card border — `.topbar` is a flat full-width band with only a `border-bottom` hairline, `.score-frame` has no border/background of its own. Both bleed to the true viewport edge with `margin-inline: calc(50% - 50vw)`, which widens them to `100vw` about their own centre; their `padding-inline: var(--body-px)` puts content back at a normal inset. **Cancelling `--body-px` alone is not enough** and was the bug behind "the top bar isn't full width" on a tablet: `body` is capped at `max-width: 64rem` and centred, so on any viewport wider than that (a landscape iPad is ~1366px) a negative margin of `--body-px` only reaches the edge of the *content column*, leaving a gutter either side. `body` carries `overflow-x: clip` so the widened children cannot produce a horizontal scrollbar (`clip` rather than `hidden`, which would break sticky positioning and programmatic scrolling). `body` has zero top padding — `.topbar` must sit flush against the viewport's actual top edge to match ScrollScore's toolbar.

The `#message` element (status/error text from `say()`/`fail()`) has no placeholder text — it's empty until the first real status is set. The local-history counter (`#history-info`, `app.js`'s `updateHistoryInfo`) lives outside the footer entirely, `position: fixed` to the viewport's bottom-left corner (`.history-badge`) rather than the footer's normal flow — on a short page the in-flow footer sits nowhere near the bottom of the screen, so pinning it is what actually reads as "bottom-left of the screen." Text is `已紀錄N題`.
- **That same viewport-relative pinning made the badge unreadable on a tall test.** It used to be plain text at `opacity: .7` with no background, so on any page whose content reaches close to one viewport height at rest (a longer score on a tablet, say — `.message`'s own in-flow text lands almost exactly at that same bottom-left corner), the two transparent, backgroundless texts landed on the same pixels and both became illegible. Fixed by giving it the same solid-pill treatment as `.badge` (border + opaque background) — it now always reads cleanly on its own, the same trade any floating chip/FAB elsewhere on the web makes: it can cover a small, fixed-size corner of whatever's behind it, but it never again turns into two-texts-of-mush.
- **The 30-second preparation message used to unconditionally claim "整份樂譜已經在畫面上" (the whole score is already on screen)**, regardless of whether that was actually true. `scripts/devices.js`'s own audit already tracks per-device whether the score fits without scrolling (`scoreBottom <= viewportHeight`) and phones routinely fail it — deliberately, since a phone is left to scroll rather than shrink into illegibility (see `fitScore` above). Real ABRSM preparation time is built around seeing the whole test at a glance — the checklist's own steps ("掃描難點", "用最難的那一小節決定速度") assume that — so telling a scrolling phone user the whole piece is already visible actively misleads them about the one thing this countdown is simulating. `scoreFitsViewport()` (`app.js`) runs the identical fits-without-scrolling check at prep time and `runPreparationCountdown()` now picks between "整份樂譜已經在畫面上" and "可上下捲動看完整份樂譜" accordingly.

The meta strip (`#meta`, `app.js`'s `showMeta`) has no labels — key, time signature, bar count and tempo print as plain values in a fixed order, separated by "丨" (e.g. `C 小調丨3/4丨12 小節丨♩≈88`). The first three fields each get a fixed CSS width (`.meta-key`/`.meta-time`/`.meta-bars`, sized above the widest possible string for that field) so the "丨" separators never shift position. `scripts/devices.js` asserts every separator's on-screen position stays fixed across regenerations.
  - **Tempo used to print the free-text term too** (`Andantino leggiero (♩≈88)`), and its unbounded length drove a run of CSS fixes now removed: a single-line ellipsis hid the BPM number entirely on some terms, a 2-line clamp fixed that but let a short term ("Waltz") share row 1 with key/time/bars while a long one ("Sadly and slowly") got pushed onto a row of its own by the browser — a discrete 1-row/2-row toggle that made the strip's height, and everything below it including the score, jump depending on which term a test happened to draw. A narrow-breakpoint `flex-basis: 100%` forced tempo onto its own row unconditionally to remove that toggle. **The term itself already prints above bar 1 in the score** (`pinTempoTermPosition`), so repeating it here was redundant; `showMeta` now prints only the metronome mark, which is always short and bounded (`♩≈46` to `♩≈168`) and never needs to wrap — `.meta-tempo` is plain `white-space: nowrap` and the clamp/ellipsis/forced-own-row CSS is gone.

## Conventions

- No build step, no bundler. `vendor/opensheetmusicdisplay.min.js` is committed directly (not `node_modules/`, which is never deployed) — see `vendor/README.md` before touching it.
- **Push straight to `main` once work is verified — do not ask first, and do not leave finished work stranded on a feature branch.** GitHub Pages deploys from `main`, so anything left on another branch is invisible on the live site regardless of how thoroughly it was tested locally; a whole session's worth of fixes once sat unmerged for days because the standing instruction had been "never push without asking." The user has explicitly overridden that for this repo.
- **Every relative ES module import reachable from the browser carries a matching `?v=N` query, and it has to move together.** `index.html` only ever bumped `app.js?v=N`/`styles.css?v=N` themselves; every file `app.js` imports (`generate.js`, `musicxml.js`, `fingerprint.js`, `theory.js`, `playback.js`, `stage.js`) and everything *those* import in turn (`random.js`, `harmony.js`, `melody.js`, `rhythm.js`, `meter.js`) had no version query of their own. A browser caches each import specifier as its own URL — bumping the entry script's query forces a fresh fetch of `app.js`'s own bytes, but its unversioned `import ... from './playback.js'` can still resolve to a stale cached copy, silently making an entire session's worth of generator/playback fixes invisible without a hard refresh. Whenever *any* file in this graph changes, bump the version query on every import in the graph (and the two tags in `index.html`) to the same new number — a partial bump defeats the point, since the whole graph has to become a new set of URLs together. `src/generator/index.js`'s re-exports are unversioned on purpose: nothing in the browser's load path imports through it (only Node scripts and tests do, which never hit this cache), so it isn't part of the graph that needs bumping.
- **Home-screen install (`manifest.json` + the `apple-mobile-web-app-*`/`mobile-web-app-capable` meta tags and `icons/apple-touch-icon.png` in `index.html`) is what actually answers "can I hide Safari's address bar/tab strip?"** — a page has no API to hide browser chrome itself, on rotation or otherwise; iOS Safari only drops it (full screen, both orientations) for a page launched from a home-screen icon in standalone mode, which is what these tags enable. The manifest's `display: "standalone"` covers Android/desktop install prompts the same way; the Apple-specific meta tags are still needed alongside it since iOS Safari doesn't read the manifest for this. `icons/*.png` are generated (a plain gold "S" on the site's own cream background, DejaVu Serif Bold) rather than hand-designed — regenerate with Pillow if the palette ever changes rather than keeping it in sync by hand.
- The rules table (`src/rules/abrsm-piano-grades.json`) is the single source of truth for per-grade parameters. Grade 5–8 are `partial`: as of 2026-08 the whole grade 1–8 table has been checked page-by-page against the genuine ABRSM specimen books (*Piano Specimen Sight-Reading Tests*, AB3394–AB3401) the user provided as PDFs, which caught real errors the earlier secondary-source-derived table had — `ff` was wrongly dated to Grade 3 (real first appearance is Grade 5; it doesn't occur once in either Grade 3's or Grade 4's 45 specimen tests), Grade 2's bar counts were wrongly given as a 4–8 range when every one of the 55 specimen tests uses a fixed length identical to Grade 1's convention, and `5/4`/`sfz` were wrongly dated to Grade 7 when Grade 6's book already has them repeatedly (`7/8`/`7/4` similarly needed adding starting at Grade 7, and `7/4` wasn't in the table at all). Exact bar-count ranges and key-signature ceilings for Grade 6–8 are still not verified against the official syllabus PDF (`www.abrsm.org` is blocked from this environment) — that's the reason `partial` rather than `verified`.
- `www.abrsm.org` and the piano sample host (`tonejs.github.io`) are blocked by this environment's egress policy — cannot be fetched directly from a session in this environment.
- Two hands are never generated independently — the left hand is written first and the right hand is checked against it (see `src/generator/melody.js`), or dissonant intervals fall out of two separate random walks.
- Any change to the follow-view (`src/app/stage.js`) or the topbar/score-frame layout should be re-verified with `npm run devices`, not just visually — several past bugs there only showed up in a real headless-browser trace.
- Tests (`test/*.test.js`) use `node --test` directly with no test-framework dependency; `test/helpers.js` holds the shared duration/XML-well-formedness assertions used across all three suites.
